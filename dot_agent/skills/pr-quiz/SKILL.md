## 目的

このスキルは、コード変更（PR またはブランチの差分）を題材にしたクイズを通じて、
**ユーザー自身が変更内容を理解すること** を助ける。

成果物は「良い問題」である。良い問題とは、diff を読み込んで変更の仕組みを理解していないと
答えられず、答え合わせの解説を読むと変更の本質がより深く分かる問題のこと。
要約の穴埋めや暗記クイズ（ファイル名・変数名・行数当て）は理解に寄与しないので出さない。

## Arguments

ユーザーから以下のいずれかが渡される:

- PR の URL（`https://github.com/<owner>/<repo>/pull/<N>`）、`#<N>`、または番号
- ブランチ名（例: `fix/SOCV2-1165/search-persister-databoost-quota`)

問題数の指定（「10問出して」等）や範囲の指定（「テスト以外で」等）が添えられていたらそれに従う。
引数がどちらとも解釈できない・何も渡されていない場合は、AskUserQuestion で対象を確認する。

## 手順

### Step 1: 変更コンテキストを集める

**PR の場合**（URL 中の owner/repo が現在のリポジトリと違っても `-R <owner>/<repo>` で同様に扱える）:

```bash
gh pr view <N> --json number,title,body,url,baseRefName,headRefName,additions,deletions,commits
gh pr diff <N>
```

**ブランチの場合**:

```bash
git fetch origin <branch>
git log --oneline origin/main..origin/<branch>     # コミットメッセージも説明文として使う
git diff origin/main...origin/<branch>             # three-dot: マージベースからの差分
gh pr list --head <branch> --state all --json number,title,body,url
```

ブランチに紐づく PR が見つかったら、その説明文も出題材料に使う（背景・意図の情報源として重要）。
ローカルにしかないブランチなら `origin/` を外して同じことをする。

### Step 2: 差分を分析する

出題前に、変更を自分が完全に理解する。以下を押さえること:

- **なぜ**この変更が必要だったか（説明文・コミットメッセージ・チケット番号から）
- 変更**前**の挙動と変更**後**の挙動の差
- 実装の中心的な仕組み（どのファイルのどの変更が本質か）
- エッジケース・リスク（どういう入力/状況で挙動が分かれるか、何が壊れうるか)
- 影響範囲（どのコンポーネント・呼び出し元に波及するか）

ノイズは出題対象から外す: 自動生成ファイル（`*_gen.go` 等）、`go.sum`・lockfile、
イメージダイジェスト更新、フォーマットのみの変更。

差分が巨大（目安 2,000 行超）なら本質的なファイル群に絞り、絞ったことと省いた範囲を
ユーザーに一言伝える。解説の正確性に自信が持てない箇所は、`git show <ref>:<path>` や
Read で周辺コードを確認してから正解を確定する。

**この段階の分析をユーザーに見せないこと。** 変更の詳細な要約を先に見せると答えの
ネタバレになり、クイズの意味がなくなる。出題開始時に伝えてよいのは
「PR #1696「<タイトル>」について全4問出します」程度の1〜2行まで。

### Step 3: クイズを設計する

**問題数**: 差分の実質規模で決める。小さい変更（〜100行）は3問、**通常は4問**
（AskUserQuestion 1回にちょうど収まる）、大きい・複数コンポーネントにまたがる変更は
7問。ユーザー指定があればそちらを優先。

**出題タイプ**: 以下から変更の性質に合うものを混ぜ、少なくとも3タイプはカバーする:

| タイプ | 問うこと |
|---|---|
| 目的 | なぜこの変更が必要だったか、何が問題だったか |
| 挙動変化 | 変更前後で何がどう変わるか |
| 実装 | 中心的な仕組みはどう動くか、なぜその方式なのか |
| エッジケース | 特定の入力・状況・タイミングで何が起きるか |
| 影響範囲 | どこに波及するか、何は変わらないか |

**選択肢の作り方**: 4択・正解は1つ。誤答の選択肢（distractor）は「diff を斜め読みした人が
引っかかる誤読」「変更前の挙動」「関連するが別の仕組み」から作ると、間違えたときの学びが
大きくなる。明らかにありえない選択肢で埋めない。

**品質チェック**: 各問題について、出題前に正解を diff の該当行で裏取りする。
裏取りできない問題は捨てて作り直す。diff を読まず一般常識だけで答えられる問題も捨てる。
解説で引用する行番号は diff のハンク位置から推測せず、実ファイル（Read または
`git show <ref>:<path>`）で確認してから書く。正解の位置は問題ごとに変え、
同じ記号が過半を占めたり、常に最長の選択肢が正解になったりしないようにする。

### Step 4: まとめて出題する

AskUserQuestion に複数問をまとめて渡し、呼び出し回数を最小にする。
**1回の呼び出しに入れられるのは最大4問**（ツールの上限）なので、標準の4問は
1回で出題する。5問以上はできるだけ均等なバッチに分ける: 5問→2回(3+2)、
7問→2回(4+3)。5問以上を1回で送ろうとするとバリデーションエラーになる。

- `header`: `Q1/4` のような全体の通し番号（バッチをまたぐ場合も連番にする）
- `question`: 設問文。必要なら短いコード片や状況設定を含める(正解が漏れない範囲で)
- `options`: `label` は要点の短い言い回し、補足が要るなら `description` に。
  「(Recommended)」は付けない（正解のネタバレになる）
- `multiSelect`: false

**答え合わせ**: バッチの回答を受けるたびに、次のバッチに進む前に、バッチ内の各問について:

1. 正解/不正解を伝える
2. 解説する — なぜそれが正解か、他の選択肢はなぜ違うかを、diff の該当箇所
   （`path/to/file.go:42` 形式）を引用して示す

ユーザーが「Other」で自由回答した場合は、正解選択肢と意味が合っていれば正解として扱う。
「わからない」「スキップ」も許容し、その場合は解説だけ示して次へ進む。

### Step 5: 結果をまとめる

全問終了後、以下を提示する。結果テーブルには各問の**設問**と**ユーザーが選んだ回答**を
必ず再掲する（答え合わせは会話の中で流れてしまうため、最後に一覧で振り返れるようにする）:

```markdown
## 結果: 3/4 正解

| # | 設問 | あなたの回答 | 正解 | 結果 |
|---|---|---|---|---|
| 1 | 変更前の initValkeyCache の何が問題だったか | 失敗するとPod寿命の間キャッシュ無効 | 失敗するとPod寿命の間キャッシュ無効 | ✅ |
| 2 | 未接続中に GetOrFetch が呼ばれるとどうなるか | WARNログ→Spanner→非同期で書き込み | ログなしでフォールバック、書き込みもしない | ❌ |
...

### この変更の要点
（3〜5行。クイズで扱った内容を軸に、変更の本質を復習としてまとめる）

### 復習ポイント
（間違えた問題に対応する diff 箇所を file:line で挙げ、何を読み直すとよいか一言ずつ）
```

- 「設問」は設問文の内容が思い出せる程度の短縮形にする（「変更の目的」のようなテーマ名
  だけに置き換えない）
- 「あなたの回答」「正解」には選択肢の `label` を使う。「Other」での自由回答はその要旨を、
  スキップは「—（スキップ）」と書く

全問正解なら復習ポイントは省き、クイズで扱わなかった補足があれば添える。

## クイズに適さない変更

依存更新のみ・自動生成のみ・イメージダイジェスト更新のような PR は、クイズにしても
学びがない。その場合は無理に出題せず、「この PR はクイズに適さないため」と理由を伝えて
1〜3行の要約を返す。

## 非対話環境でのフォールバック

サブエージェントや CI など、ユーザーと対話できない環境で実行された場合は、
Step 4〜5 の対話ループの代わりに、全問を `quiz.md` にまとめて出力する
（保存先の指示があればそれに従う）。読み手がまず自力で解けるように、
**設問部と解答部を分離する**。設問の直下に正解を書くと目に入ってしまい、
自己テストとして使えなくなる:

```markdown
# <PR タイトルまたはブランチ名> 理解度クイズ

## 設問

### Q1: <設問>
- A. <選択肢>
- B. <選択肢>
- C. <選択肢>
- D. <選択肢>

（Q2 以降も同様に設問だけを並べる）

---

## 解答と解説

### Q1 — 正解: B
<diff の該当箇所を file:line で引用した解説。他の選択肢がなぜ違うかも書く>
```

Step 1〜3（コンテキスト収集・分析・品質チェック）は対話時と同じ水準で行うこと。
